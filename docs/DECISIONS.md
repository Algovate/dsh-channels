# 决策记录

每条都是"当时为什么这样"，按时间顺序。写完的实现结果在 [STATUS.md](STATUS.md)。

## ADR-1：新插件，不是旧插件的 fork

**背景**：上一代 `dsh-plugin-weixin`（5.9k 行，含一个巨大的客户端 bundle）已经在真机上跑了几个月，
功能更多。

**决定**：另起一个仓库 `dsh-channels`，把"通道无关"的那三分之一下来，适配器重写成薄翻译层。

**理由**：fork 会把旧插件的形状（微信特有的状态、记忆、生活模拟、UI）都带进来，每加一个通道
就要再多一份；新插件的检验标准是"**第二个通道能不能不加核心代码就接上**"。M5 证明可以。

**代价**：旧插件的能力（记忆、预算、生活状态、命令目录）没有迁过来，需要时按需重做，
而不是整块搬迁。

## ADR-2：默认拒绝，不做"第一个说话的人自动入册"

**背景**：参考实现为了开箱即用，把第一个给 bot 发消息的人自动加进白名单。

**决定**：空白名单 = 谁都不能驱动 agent。第一个陌生人只会被拒，日志里有他的 id。

**理由**：把部署安全性交给"谁先发消息"是运气。这个插件会被别人装、会被公网机器人挂、
会被放进多人的群；自动入册意味着任何先到的人都能指挥你的 agent。

**代价**：首启要多一步：从日志或 `/whoami` 拿 id，写进 `config.json`（或卡片里点一下）。值得。

## ADR-3：适配器是库，不是加载器行

**背景**：Cordis 的通道插件通常是 bundle，每个通道一条 `insert` 行。

**决定**：只有核心是 bundle；适配器是普通包，核心在 `apply` 里按 `adapters` 名字 `import()`。

**理由**：装第二个通道不该改 patch、也不该多一条可能悬空的行；`adapters` 数组是唯一开关。
卸载适配器只需删一个包名。

**代价**：适配器不能自己注册 loader 行或客户端 bundle（见 ADR-9）。

## ADR-4：一个会话一个 DSH session，id 由会话键派生

**决定**：`sessionIdFor(target) = chan-<channel>-<sha1(channel|account|conversation)>`，不随机。

**理由**：重启、重装、换机器都要接回同一条会话线；随机会让每次重启都开新会话，历史散落。
`/new` 用追加"线号"的方式开新线，旧线不动。

**代价**：改会话键（比如换 accountId）会开新会话；这是显式的，不隐藏。

## ADR-5：交互答复 bypass 回合队列

**决定**：有提问/审批挂起时，入站消息先尝试被它消费；消费成功就不进回合队列。

**理由**：排在"正在提问的回合"后面 = 死锁到 10 分钟超时。门链仍然先跑，陌生人不能替你回答。

**代价**：答复路径有两条（注意别在两边重复实现解析）。

## ADR-6：限流计数进宿主的存储域

**决定**：`senderPerMinute` / `senderPerDay` 的计数存宿主 `channels` 存储域；没有域时回落
`counters.json`。

**理由**：内存计数重启清零，"每人每天 60 条"就是装饰。域提供原子、校验、跨进程的 KV；
读同步满足闸门（闸门不能 await），写穿满足持久。

**代价**：宿主包只能作为 **optional peer** + 动态 `import()`。装成普通依赖会把宿主的行挤坏
（实测宿主禁用了自己的 `storage-domain` 行）。

## ADR-7：journal 两段式，而不是"发送成功后记一条"

**决定**：调用适配器前写 `sending`，返回后写 `settled`（accepted/unconfirmed/failed + id/code）。

**理由**：只有两段才能回答"日志说发了、手机没收到"。单段日志在进程崩溃时无法区分"没发"和
"发了但没记上"。只有 `sending` 的行就是 pending，这就是答案。

**代价**：每条消息两行，文件大一倍（可接受：一天几百条）。

## ADR-8：状态卡片用宿主 HTTP 路由，而不是 Typert Remote

**背景**：卡片要读宿主的实时状态。`api-remotes` 的浏览器半边只挂载**构建期生成**的
`/remote` 工件，运行期新注册的 namespace 不会出现在 `ctx.remote` 里。

**决定**：宿主用 `ctx.webServer.register` 注册三个同源路由（status/allowlist/settings），卡片
用 `fetch` 读；`Remote` 那半边仍然保留，等能生成工件时切换。

**理由**：这是唯一今天就能工作、且有明确安全边界的方案：同源、POST 校验 `Origin`、只返回卡片要显示的东西。

**代价**：路由是未认证的（本机 127.0.0.1）；同机能读 `config.json` 的人本来就能改它。

## ADR-9：客户端 `CHANNELS` 是静态表

**决定**：Chat 行的注册写在 `packages/core/client.js` 的 `CHANNELS` 数组里，新适配器要手加一行。

**理由**：浏览器看不到宿主的注册，客户端注入在服务返回 `undefined`（`ctx.get` 拿不到宿主服务），
而 namespace 需要构建期工件（ADR-8）。

**代价**：新通道必须改核心的客户端文件。这条缝隙写进了 [ADAPTERS.md](ADAPTERS.md)。

## ADR-10：`ctx.inject` 而不是 `ctx.get`

**决定**：读可选宿主服务一律 `ctx.inject(['<service>'], cb)`。

**理由**：真机上 `ctx.get('storageDomain')`、`ctx.get('workspaceRegistry')`、`ctx.get('agentPresets')`
返回空，服务明明在跑。`inject` 的回调只在服务存在时执行，也正是文档要求的写法。

**代价**：回调是异步的，需要在启动阶段包一层 Promise。

## ADR-11：失败一律是值，不是异常

**决定**：适配器的 `send`/`transcribe`/`download` 都返回结果对象；核心的发送失败进 outbox，
媒体失败只记日志，计数落盘失败只 warn。

**理由**：一条消息的失败不该让轮询循环崩、不该让另一个会话卡住、更不该让"计数没存上"变成
"你的消息被拒"。

**代价**：调用点要显式处理三种状态（accepted/unconfirmed/failed），不能靠 try/catch 兜底。
